# 物件詳細ページの制作記録

**対象**:架空の不動産会社サイト「株式会社ヒラキヤ不動産」の物件詳細ページ(実装順 2)
**期間**:2026-09-09 〜 09-14
**記録の範囲**:判断ログ J-037〜J-079、失敗記録 F-005〜F-009 のうち、このページに関わるもの

このサイトは**制作の記録を残すために作った架空のサイト**です。会社名・住所・電話番号・免許番号・人名・物件情報はすべて架空で、住所の番地は `0-0-0`、電話は `03-0000-0000`、免許番号は `000000` に統一しています。実在の会社・物件とは関係ありません。

この文書は2部構成です。**§1〜§4 は非エンジニア向け**(何を考えて作ったか)、**§5〜§6 はエンジニア・制作者向け**(実装の判断と失敗の切り分け)です。

判断の主体は毎回書き分けます。**「AI の初案」= Claude が最初に出した案**、**「SHIN の判断」= 制作者が実物を見て決めたこと**です。AI が出した案をそのまま採用した場合も、そう書きます。

## 1. このページで何を作ったか

物件1件の情報を見せて、内見予約・問い合わせにつなげるページです。架空の物件60件(賃貸40・売買20)すべてに対して、ビルド時に静的なHTMLを生成しています。

### 動いているもの(実物で確認済み)

| # | 機能 | 中身 |
|---|---|---|
| 1 | 写真ギャラリー | メイン画像+サムネイル。画像を押すと全画面で開き、左右の矢印・キーボードの ← → ・スマホの横スワイプで送れる。間取り図は最後に並ぶ |
| 2 | 物件名・価格・状態 | 新着 / 値下げ / 商談中 / 成約済みのバッジ。家賃は管理費・敷金・礼金を並記、売買は管理費+修繕積立金の月額合計を並記 |
| 3 | 右カラムの「決め手」 | 駅徒歩+町名 → 価格 → 間取り・面積・階 → 設備 → 築年・向き・入居可能日・2駅目の順に並べ、その下に予約と問い合わせのボタン |
| 4 | 物件データ | 開閉する3つの区分(入居前に確認すること / 建物 / 契約・掲載)。最初は「確認」だけ開いている |

| 9 | 成約済みの扱い | ページを消さず「この物件は成約しました」と出し、内見予約のボタンだけ隠す |
| 10 | スマホの固定ボタン | 画面下に 電話 / LINE(ダミー)/ 内見予約 |

## 2. 判断のグループ

### グループ A:何を先に見せるか

**代表:J-039「関心の高い情報を、価値の薄い情報と同じ列に並べない」**

AI の初案は、21項目を1列に並べた素の表でした。設計としては間違っていませんが、実物を見ると、駅からの距離も次回更新予定日も同じ大きさで並んでいました。

SHIN の判断:「頻出する用語をタグ化することでユーザーが条件を切り分けるときの判断材料になる。関心のある情報が情報価値の薄い他の情報と同じように並んでいると、探すのにストレスがかかる」。これを受けて、(1) 右カラムに要約4項目、(2) 本文の上にデータから導き出した「ポイント」タグ、(3) 表を4区分に分ける、の3つを同時に決めました。

この判断はこのページだけの話ではないので、**デザイン基準の原則として一般化**しました(03 §1「情報の優先順位」)。以降、一覧カードの情報量(J-046)もこの原則から決めています。

**代表:J-047「強調はするが、誇張はしない」**

「表っぽいレイアウトは古く見える。重要な情報を目立たせたい。ただし誇張に見えないように」という SHIN の要望に対し、AI が4案を出しました(SHIN が案 A を選択)。

ここで SHIN が出した懸念が「大きな数字で強調すると、良い物件に見せかけているように読めないか」でした。AI はこれに対して**3つの条件**を返し、SHIN がそれを採用しています。

1. 項目は全物件で固定する(値が良いものだけ目立たせない)。欠けている値は「—」と出す
2. 値だけを書き、「駅近」「広々」のような形容を付けない
3. 文字は本文より1段だけ大きくし、必ずラベルを付ける

不動産広告は誇大表示が法律で規制されている分野です。**「目立たせる」と「盛る」の線をどこに引くかを先に決めてから作った**のが、このグループの中心です。

| その他 | 決めたこと |
|---|---|
| J-054 | 表の区分を「データの種類順」から「読む人の関心順」に組み替え(入居の条件 → 建物と所在地 → 契約と掲載) |
| J-059 | 強調する項目を5つから3つ(立地・価格・広さ)に絞る |
| J-063 | 3項目の値の文字を1段大きく。3つとも同じ大きさにする(1つだけ大きくしない) |
| J-070 | 右カラムと下の表で同じ情報が二重に強調されていたので、下を廃止して右カラムに集約 |

### グループ B:押せるものを、押せると分かる形にする

**代表:J-052「押せるものは2種類に統一する」**

AI が出した案の中から SHIN が選ぶ形で決めました。詳細ページで押せるものは、**枠線のチップ**(設備・種目・ポイント)と**色付きの文字**(沿線・間取り・所在地・駅名)の2種類だけにし、押せないもの(金額・築年・面積・物件番号など)は本文と同じ黒のままにしています。

区別の基準も決めました。**塗り = 状態、線 = 分類でありリンク**。新着・値下げのバッジは塗りのまま、リンクになるタグは線と文字の色だけで示します。「押せそうに見えるのに押せない」を作らないための規則です。

**代表:J-051「属性から一覧へ戻す」**

SHIN の判断:「物件のすべての情報をタグなどにして整理する目的と、属性に興味を持つユーザーがいた時の回遊率を上げるため」。駅名・沿線・間取り・設備・町名を、その条件で絞り込んだ一覧へのリンクにしました。

ここで同時に決めたのが**リンクにしないもの**です。向き・入居可能日・階・面積・築年・金額はリンクにしません。理由は「一覧の絞り込みに無い条件だから」。押せる=その条件で探せる、を崩さないためです。

| その他 | 決めたこと |
|---|---|
| J-066 | 選択中のサムネイルの枠を 2px の青緑に。選んでいない枠も 2px のままにして、選び直しても画像が動かないようにする |
| J-067 | 矢印・閉じるボタンのカーソルを指の形に。拡大を開く画像だけ虫めがねの形に |
| J-071〜J-074 | アイコンの大きさを隣の文字に合わせ、揃え方(中央かベースラインか)を文字の大きさで決める。価格のアイコンは目立ちすぎるので外す |

### グループ C:情報量を減らさずに畳む

賃貸で21項目ある物件データを全部出すと縦に長く、全部隠すと「情報が少ないサイト」になります。

SHIN の判断は「入居条件の優先度の低い情報をアコーディオン内に収めて情報の煩雑さを回避」(J-060)。**項目そのものは1つも減らさず**、最初に開いている区分を「入居前に確認すること」だけにしました。

実装上の条件もここで決めています。**開閉に JavaScript を使わない**(ブラウザの標準機能で作る)、**閉じていても中身は HTML に存在する**。検索エンジンから見えなくなるのを避けるためです。

| その他 | 決めたこと |
|---|---|
| J-061 | 開閉する見出しの印は左側に1つだけ。右端に矢印を置くと、画面が広い時に見出しから1000px以上離れて「矢印だけを押すもの」に見える |
| J-062 | 1つのアコーディオンに11項目入ると開いた時に減った気がしないので、2つに分ける |
| J-076 | 見出しを「物件概要」から「物件データ」に変更。3つの区分を同じ形に統一 |

### グループ D:写真の見せ方

**代表:J-048 / J-049**

SHIN の判断:「物件画像をギャラリーにして確認しやすくしたかった」。画像を押すと全画面で開き、矢印・キーボード・スワイプで送れる形にしました。**ライブラリは足さず**、ブラウザ標準の機能(`<dialog>`)と CSS だけで作っています。

その後、SHIN が実物で操作して「切り替わるのが分からないと操作しているか判別しづらい」と判断し、写真の送り方を**横にスライドする動き**に変更(J-049)。端まで来たら最初に戻りますが、**巻き戻す向きには動かさない**(同じ向きのまま次へ続く)ようにしています。

このグループには失敗記録が2件(F-007・F-008)あります。詳細は §5。

写真が0枚の物件が60件中3件あります(意図的にそういうデータを作りました)。その場合は「写真準備中」と出し、押すと間取り図だけが開きます。

### グループ E:次の行動に運ぶ

| J-ID | 決めたこと | 誰が |
|---|---|---|
| J-038 | 成約済みの物件では内見予約を出さない。「成約済み」と「新着」を同時に出さない。売買は「内見」ではなく「見学」と呼ぶ(業界の言い方) | AI の初案12件のうち、SHIN がこの4件に条件を追加 |
| J-050 | 本文から電話ボタンを外す。「電話ボタンが多いのと、ここでは問い合わせにつなげたい意味でなくした」 | SHIN |
| J-064 / J-065 | 最近見た物件を、横スクロールから矢印で1件ずつ送るカルーセルに | SHIN(1画面送り → 1件送りは2回目の判断) |
| J-075 | 予約と問い合わせのボタンを左右に並べる。狭い幅で「この物件を問い合わせる」が2行になったので「問い合わせる」に短縮 | SHIN |
| J-079 | 下部のボタンを「他の物件」より前に移動。「他の物件を見た後に CTA が来る並びだったので、前に移した」 | SHIN |

J-079 は、**流れの向きが逆になっていた**という指摘です。この物件の情報 → この物件への行動 → 他の物件、の順に直しました。

### グループ F:架空であることを保つ

架空のサイトなので、実在の会社・物件と間違えられないことが要件です(制作計画 §7-9)。

| J-ID | 決めたこと |
|---|---|
| J-053 | 担当者の写真はプレースホルダー(人型のシルエット)で、実写真は使わない。氏名は「架空」「見本」「仮名」の姓で架空と分かる形 |
| J-077 | そのプレースホルダーの品質が低かったので作り直し。画像内の文字は「架空・プレースホルダー」の1行だけ残す(画像だけを見た人にも架空と分かるように) |
| J-078 | 担当者の紹介文を約100字から150〜200字に。**その物件のデータから組み立て、データに無い事実は書かない** |

J-078 では、それまでの文章にあった「平坦な道のりで通勤にも便利」「周辺にはスーパーやコンビニがそろい」といった表現を削りました。**架空の物件なので、その周辺に何があるかを裏付ける情報が存在しない**ためです。区・町・駅・徒歩分・築年・構造・階数・面積・設備・費用など、データとして持っている値だけで文章を組み立てています。

地図も同じ考え方で、「架空の住所のため、ピンの位置は町の代表座標付近です」とページに書いています。

## 3. 実物を見て判断が変わったもの:物件データの区分を4回作り直した

このページで最も往復が多かった箇所です。**初案が一度で決まらない前提**で進めた記録として残します。

| 回 | 形 | 変えた理由(誰が) |
|---|---|---|
| 0 | 21項目を1列に並べた素の表 | AI の初案 |
| 1(J-039) | 4区分(基本 / 費用 / 建物 / 契約・掲載)、PCは2列 | 実物を見て「表がシンプルすぎる」(SHIN) |
| 2(J-047) | 見出しの下に「キー項目の帯」5項目 + 罫線だけの表 | 「表っぽいレイアウトが古く見える。重要な情報を目立たせたい」(SHIN。AI の4案から選択) |
| 2'(J-047 追記) | 帯を薄い地色から**白いカード**に | 実物を見て「帯が背景に溶けて、項目が離れてまとまりがない」(SHIN) |
| 3(J-054) | 区分を「データの種類順」→「読む人の関心順」に | 「未計画のまま情報を配置したため、レイアウト以前の問題として情報を整理する」(SHIN) |
| 4(J-059) | 帯の5項目を**3項目**(立地・価格・広さ)に | 「優先度の高い情報が分からないので検索して調べた」(SHIN。→ §4) |
| 5(J-060) | 3項目 → 設備 → 確認 → 詳細(アコーディオン)の4段に | 優先度の低い情報を畳んで煩雑さを回避(SHIN) |
| 6(J-070) | **3項目を廃止**し、決め手は右カラムに集約 | 「右カラムと物件概要で同じ情報が二重に強調されていた」(SHIN) |
| 7(J-076) | アコーディオン3つに統一。見出しを「物件データ」に | 「設備と3項目が移動して軽くなったので、アコーディオンに統一して整理された形にした」(SHIN) |

7段階のうち、**AI が起点になったのは 0 と 2 の案出しだけ**で、残りはすべて SHIN が実物を見て出した条件です。

注目したいのは、**2 で足したものを 6 で自分で捨てている**点です。強調のための帯を作り、3項目に絞り、最後に「右カラムと重複している」という理由で丸ごと廃止しました。作った本人が捨てる判断をしないと、重複したまま残ります。

この過程で2回、**別の情報が巻き込まれて消えかけた**ことも記録しています。

- J-059 で売買の面積を帯に移し、J-060 で表から消したため、**売買物件の面積がどこにも無い状態**になっていた。J-070 で表に戻した
- J-060 で「交通」の行を消す時、その中に入れていた沿線と2駅目も一緒に消えるところだった。気づいて「建物」の区分に移した

「表示を整理する」作業は、**整理した結果どの情報が残るかを毎回数え直さないと、静かに欠落する**という例です。

## 4. 外部の根拠を使った判断

自分の感覚だけで決めていない箇所を挙げます。

**1. 何を先に見せるか(J-059)**

SHIN が「優先度の高い情報が分からないので検索して調べる」として、住宅を選ぶ時に重視される条件の一般的な順序(**立地 → 価格 → 間取り・広さ**)を確認し、その順に3項目を並べました。売買では毎月の支払い(ローン+管理費+修繕積立金)で判断されることが多いという前提から、価格の下に管理費+修繕積立金の月額合計を添えています。

**2. 業界の表示ルール(01 設計図・2026-09-05 の決定)**

取引態様・情報更新日・次回更新予定日を必ず出す、と設計段階で決めています。設計図には「**AI はこれを出さない**」と書いてあり、実際に AI の初案には入っていませんでした。不動産広告では扱いが決まっている項目で、知らないと欠落します。

**3. 「見学」と「内見」(J-038)**

売買物件のボタンは「内見」ではなく「見学」にしました。賃貸と売買で呼び方が違うという業界の言い方に合わせたものです。

**4. 参考にしたサイトと、外したもの(03 §1)**

検索の入口・条件の並び・カードの情報順は大手不動産ポータル(LIFULL HOME'S)を参考にし、フッターの構成は別の1社を参考にしています。一方で、右カラムの広告・ランキング・記事・通知・写真主体のレイアウトは**意図的に外しました**。地域の仲介会社のサイトとしては情報が多すぎるためです。

**5. 地図に Google を使わない理由(J-005)**

Google Maps Platform は 2025年3月に月200ドルの無償枠が廃止され、課金アカウントの登録が必要になりました。このサイトは「無料で使えるものだけで構成する」方針なので、OpenStreetMap + Leaflet を採用しています。**技術的な優劣ではなく費用の判断**で、実案件ならクライアントの課金アカウントで Google を使うのが普通だという違いも記録しています。

なお、OpenStreetMap のタイル提供元の利用条件は**まだ確認しきれていません**(商用利用に SLA が無いことは確認済み)。公開前(実装順 9)に再確認する宿題として記録に残しています。

## 5. 失敗5件と、その型の違い

**ここからはエンジニア・制作者向けです。**

このプロジェクトでは「AI が間違えて、制作者が気づいたもの」を F-ID で記録しています。詳細ページに関わる5件は、**原因の層がそれぞれ違います**。

### F-005:データの「順序」に意味があることを仕様に書いていなかった

一覧カードで曳舟の物件が「押上駅 徒歩8分」と表示された。WordPress の駅タクソノミーが名前順で値を返し、変換スクリプトが配列の1番目を最寄駅と決め打ちしていた。**最寄1駅目を専用のフィールドで持つ**ように変更して解決。

さらに追記がある。修正後も開発サーバーでは古い表示が残った。原因は開発用の `fetch` が `force-cache` で、再投入前の応答がキャッシュに残っていたこと。`no-store` に変更した。

> **型**:仕様の穴。「配列の順序」を書かないと、AI は返ってきた順を意味のある順だと思い込む。加えて「キャッシュ戦略を明示する」だけでは足りず、更新を見たい経路は明示的に無効化する必要がある。

### F-006:AI の確認手順が、制作者の環境を壊していた

制作者の開発サーバー(ポート3000)が繰り返し落ちた。原因は AI がスクリーンショットを撮った後に、**ポート3000 のプロセスをまとめて停止していた**こと。以降、確認用サーバーは3001に固定し、停止するときもポート番号を確認して該当プロセスだけを落とす手順に変えた。

> **型**:成果物ではなく作業環境の事故。AI の確認手順が本人の環境(ポート・プロセス・キャッシュ)に触っていないかを先に確かめる必要がある。この件を受けて、破壊的なコマンドは実行前に確認を求める設定を入れた。

### F-007:「効いた」を1点だけで確認していた

拡大したギャラリーで、画像の外側(灰色の部分)を押しても閉じなかった。原因は、画像を収める箱と実際に絵が描かれている範囲が一致しないこと。画像の箱は 1248×750 まで広がるが、絵があるのは中央の 1125×750 だけで、**左右 61.5px の余白も画像の当たり判定に入っていた**。

見逃した理由もはっきりしている。AI の動作確認は「閉じた」を1点(x=6)だけで確かめており、その点はモーダルの内側の余白で、**症状が出る帯(x=16〜78)を外していた**。

修正は、判定を「画像の要素かどうか」から「絵が描かれている範囲の中かどうか」に変更。元画像の寸法から計算する純関数を作り、テストを3件足した。

> **型**:確認方法の不足。面で効く操作は、効く場所と効かない場所の**両方**を押して確かめる。

### F-008:見えているものの正体を取り違えた

拡大中のギャラリーで、2枚目を選んでいるのに1枚目のサムネイルに青い塗りが乗る。矢印を連打すると出る。

チャット側の AI の見立ては「フォーカスの標準表示」だった。**これは実測で否定された**(`:focus-visible` が false)。真の原因は**テキスト選択**。矢印を速く続けて押すとダブルクリックと判定され、アイコンだけのボタンには選択できる文字が無いため、選択範囲が隣のサムネイル画像まで伸びていた。選択ハイライト(ブラウザ既定の青)が画像の上に乗って「青い塗り」に見えていた。

修正はサムネイルとメイン画像に選択禁止を付けるだけ。キーボードのフォーカス表示には触っていないので、Tab で操作したときの枠は残っている。

> **型**:症状と原因の取り違え。「青く見える」= フォーカスとは限らない。選択・ハイライト・背景のどれかを、計算後のスタイルと選択範囲の API で切り分けてから直す。

### F-009:重ね合わせの境界を疑うべきだった

地図までスクロールすると、地図のタイルとズームボタンがヘッダーの上に重なった。

原因は、地図ライブラリが子要素に自前の重なり順(タイル200 / マーカー600 / コントロール1000)を持つ一方で、**その入れ物自身が重ね合わせコンテキストを作っていなかった**こと。そのため子の値がヘッダーの値と同じ土俵で比較され、常に地図が勝っていた。

修正は入れ物側にコンテキストを作って子の値を内側に閉じ込める1行。地図の中の順序はライブラリの値のままなので変わらない。

> **型**:層の取り違え。「重なりが足りない」と見えても、個々の値を上書きするのではなく、**境界を作って閉じ込める**。個別に上書きすると、ライブラリの更新で内部の順序が壊れる。

### 5件の並べ方

| F-ID | 層 | 誰が気づいたか | 一般化できること |
|---|---|---|---|
| F-005 | データの仕様 | 制作者(実データの矛盾) | 順序に意味があるなら仕様に書く |
| F-006 | 作業環境 | 制作者(自分の環境が壊れた) | AI の手順が環境に触っていないか確かめる |
| F-007 | 確認方法 | 制作者(実機で操作) | 効く場所と効かない場所の両方を試す |
| F-008 | 原因の切り分け | 制作者(実機で連打) | 見た目の症状から原因を決めつけない |
| F-009 | 実装の層 | 制作者(実機でスクロール) | 値ではなく境界を疑う |

**5件とも、気づいたのは制作者**です。AI は指示された範囲では正しく動いており、F-007・F-008 は AI 自身の確認が通ってしまっていました。この非対称は、そのまま「AI に任せられる範囲」と「人が見る必要がある範囲」の線になります。
