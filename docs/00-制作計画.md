# AI制作記録サイト 制作計画

**作成日:2026-09-04 / 更新:2026-09-05**
**位置づけ:制作と記録の設計をまとめたもの**

---

## 1. 目的

AIを使って一からWEBサイトを制作し、**その経緯・意図・判断をすべて記録する**。完成物ではなく記録を成果物とし、AIを活用できる人材であることの証明に使う。

制作範囲は4つ:**ディレクション / デザイン / コーディング / UI・UX**。UI・UXは実装するだけでなく、なぜその設計にしたかを言及した状態にする。

### 1-1. Nordic Works があるのに新規で作る理由

Nordic Works(架空B2B SaaS企業のメディア+コーポレートサイト・ヘッドレスWP構成)は成果物としては同等水準にあるが、**制作時の記録が残っていない**。以下は完成物から復元できないため、新規制作でしか取得できない。

1. AIの初案そのもの(スクリーンショット・生成コード・出力テキスト)
2. 却下した案と、却下した理由
3. プロンプトの変遷(なぜ言い直したか)
4. 詰まった箇所と、そこに要した時間
5. 判断の順序(どの決定が後続を縛ったか)

題材が既存作品と近くても問題にならない。**記録が目的であり、サイトは記録を発生させるための装置**であるため。

**訂正(2026-09-05・リポジトリ確認後):** Nordic Works に記録が「ない」は誤り。`docs/` に設計ドキュメント9本と週次作業ログ21本、README に「工夫した点/解決した落とし穴」8件・「意図的にやらなかったこと」5件、`docs/08-portfolio-prep.md` に「語れるエピソード」6本(課題→原因→対処→伝わるポイント)が残っている。**残っていないのは上記1〜5(初案・却下理由・プロンプト変遷・詰まりの時間・判断の順序)と実測時間のみ。** 判断の「結果」は記録されているが、判断の「過程(AIとの往復)」と「数字」がない、が正確。

## 2. 証明する対象(証明しないもの)

| 証明する | 証明しない |
|---|---|
| AIで作る過程で、人が何を判断したか | 「AIで完結できる」こと |
| AIが出せない領域を、どう埋めたか | 実装スキルの網羅性 |
| AIの出力が間違っている箇所に気づけること | 制作速度の速さ |
| 4範囲を一人で通した判断の一貫性 | 高度な技術の使用 |

**理由:**「AIで作れる」はAIツール・AI講座の販売側が既に大量に主張しており、差別化にならない(検証記録§25-26)。また「実装できる」は受注に結びついていない(プロフィール掲載のReact/Vue/Nuxtから0件、ココナラのAIO/LLMO出品の88〜90%が0件・§38/§41/§42)。

**買い手側の状況:** AIで自作して途中で止まった層が実在する。買い手側レビュー(2026-09-02「AIに聞きながら頑張ったが、早くお願いすればよかった」)と、売り手側の商品化(福山市MUDORA・2026年7月「AIで作ったホームページのサポート」)が独立に同じ現象を指している。彼らが必要としているのは「AIで作れる」証明ではなく、**どこで崩れて誰がどう直すかを知っている人**の証明。

## 3. 記録の設計

### 3-1. 記録する4種

| 種別 | 内容 | 対応 |
|---|---|---|
| ① 判断ログ | AIの初案 → 自分の判断 → 修正後(3点セット)。判断の出所も書く | §43-B「課題の背景・選択の理由・結果と学び」 |
| ② 実測 | 工程別の実働時間、AI初案の採用率、手戻り回数 | §43-B「結果を数字で」/ 計測シート1件目 |
| ③ 失敗と学び | AIが間違えた箇所、気づけた理由、任せる/任せない判断 | §43-B「失敗と学び」/ §43-C「向き不向きの言語化」 |
| ④ ガバナンス | 使用ツール・プラン・生成範囲・素材の権利・機密情報の扱い | §43-C「AIガバナンスの1枚」 |

### 3-2. 記録の粒度(重要)

全工程を等しく記録すると量が破綻する。**判断が発生した瞬間だけ**を記録する。

- **記録する:** AIの案を却下した / 条件を足して出し直させた / AIが出せないので自分で決めた / AIの出力が間違っていて気づいた
- **記録しない:** AIの案をそのまま採用して問題がなかった箇所。「そのまま採用」と1行だけ残す

「そのまま採用した割合」自体が数字になる(**初案採用率**)。

### 3-3. 一次記録の取り方

- AIとの会話ログがそのまま一次記録になる(プロンプトと出力が全部残る)。後から「初案→判断→修正後」を抽出できる
- **スクリーンショットのみ別途必要**(デザイン初案・崩れた表示・エラー画面)。撮り逃すと復元不可
- **記録シートは着手前に用意する。** 制作を始めてからでは初案が失われる

### 3-4. 4範囲それぞれで記録すべき判断

| 範囲 | AIが出せないため人が決めること(=記録の中身) |
|---|---|
| ディレクション | 誰に何を売るサイトか / 成功条件 / ページ構成の優先順位 / スコープの線引き(やらないことの決定) |
| デザイン | 色・余白・文字サイズの基準 / 参考にしたものと外した理由 / 業種に合うトーン |
| コーディング | レンダリング構成(SSG/ISR/SSR)の選択理由 / コンポーネント分割の境界 / AIの提案を却下した箇所 |
| UI・UX | 導線の順序 / フォームの項目数 / 迷いどころの解消 / **その判断の根拠**(「なんとなく」ではなく業種の行動から逆算する) |

## 4. 章立て:素人が止まる6箇所

記録の公開時の章立て。素人との差が最も分かりやすく出る場所を章にする。出所は、AI自作サイトのサポート事業者が挙げた症状(MUDORA・2026年7月)と、検証記録の各章。

**冒頭に置く1文(帯の区別):**
「AIで作ったサイトが崩れたら直します」ではなく、**「AIで作ると止まる6箇所を、最初から止まらないように設計した記録」**。前者は3,000円帯、後者は設計の帯。読み手の期待値をここで固定する。

### 章1:スマホで崩れない
- 症状:文字と画像が重なる / はみ出る / ボタンが押せない
- 素人が止まる理由:AIはPC幅の初案を出す。素人は実機で見ない
- 通り方:デザイン段階でモバイル幅を先に決める。実機3種(iOS Safari / Android Chrome / PC)で確認してから公開
- 数字:確認端末数、修正箇所数

### 章2:デザインがまとまる
- 症状:ページごとに雰囲気が違う / 何を見せたいか分からない
- 素人が止まる理由:AIは1画面ずつ生成する。素人は全体の基準を持たない
- 通り方:業種の慣習と目的から、色・余白・見出しの基準を先に1枚にする。AIにはその基準を渡してから生成させる
- 数字:初案採用率

### 章3:問い合わせフォームが動く
- 症状:送信しても届かない / 迷惑メール行き / スパムが来る
- 素人が止まる理由:見た目は生成できるが、送信先・SPF/DKIM・スパム対策・確認画面は生成されない
- 通り方:送信テスト(自分宛+別ドメイン宛)、迷惑メール判定の確認、スパム対策の設置、送信後の動線まで
- 数字:テスト送信件数、到達/不達

### 章4:公開できる ※2026-09-05 書き換え(Vercel構成に合わせて)
- 症状:ビルドが通らない / 環境変数が効かない / ローカルでは動くのに本番で画像が出ない / 表示が遅い
- 素人が止まる理由:ローカルで動くことと本番で動くことの差を、AIは扱わない
- 通り方:Vercelへのデプロイ、ビルドエラーの解消、環境変数の扱い、画像最適化、独自ドメイン設定
- 数字:Lighthouseスコア(公開前後)、公開までの実働
- **書けないこと:** レンタルサーバー設置 / FTP / SSL発行 / サーバー側キャッシュ設定(Vercel構成では発生しないため)

### 章5:WordPressに組み込める ※2026-09-05 出所変更(過去実績から書く)
- 症状:HTMLはできたが更新できない / テーマに入れると壊れる / プラグインが競合する
- 素人が止まる理由:AIは静的HTMLを出す。WPのテーマ構造・更新性・プラグイン相性は別の知識
- 通り方:どこを客が触れるようにするかを先に決めてからテーマ化する
- 数字:客が更新できる箇所数、プラグイン数(少ないほど負債が少ない)
- **8年・75件の中心領域であり、最も差が出せる章**
- **出所:** 新規サイトはヘッドレス構成のためテーマ組み込みは発生しない。**既存のWP制作実績から書く**。初案・プロンプト変遷などの一次記録は残っていないが、「客が更新できる箇所をどう決めたか」「プラグインをどう絞ったか」といった判断は経験から記述可能。6章構成は維持したまま、この章のみ出所が異なる

### 章6:AIに頼んでも直らない箇所を、人が直す
- 症状:同じ指示を繰り返しても直らない / 直すと別の場所が壊れる
- 素人が止まる理由:原因の切り分けができないと、AIへの指示が症状の言い直しになる
- 通り方:原因を特定してから指示する。任せる/任せない判断を明記
- 数字:手戻り回数、人が手で直した箇所数

### 末尾に置く2つ
- **実測まとめ:** 工程別実働 / 初案採用率 / 手戻り回数 / 公開までの合計。計測シートの1件目
- **ガバナンス1枚:** 使用ツールとプラン / AIが生成した範囲 / 画像・素材の権利 / 参考にしたものの扱い / 機密情報の入力ルール

## 5. 決定事項と未決定事項

### 5-1. 決定済み(2026-09-05)

| 項目 | 決定 | 理由 |
|---|---|---|
| **技術構成** | **(a) ヘッドレスWP**(Local + Git + Vercel) | Vercelにそのまま載せて公開できる手軽さを手放したくない / レンタルサーバーの月額費用(月500〜1,500円)が不要 / WordPressテーマでの制作実績は既に複数あるため、記録のためだけに新規で作る必要性が薄い |
| **題材の方向** | Nordic Works と**別業種** | 差分を作る主役。B2B SaaS のメディアサイトとは全く違う方向に振る |
| **規模の原則** | **判断が発生する最小限** | 「機能は少ないほど良い」ではない。小さくしすぎると判断が発生せず、記録すべきものが出てこない。**6章のうち最低3箇所(章3フォーム / 章4公開と速度 / 章6切り分け)を通る規模**を確保する |

**検討の経緯(技術構成):** 一度は (b) WordPressテーマを推奨した(章5が書ける / AIが最も壊す領域で記録材料が濃い / 市場の症状と一致する)。しかし「既にWP制作実績が複数ある」という情報により、章5を新規制作で取得する必要がなくなったため撤回。

### 5-2. 既存構成の実態(2026-09-05 判明)

Nordic Works の運用構成:
- WordPress は **Local(ローカルアプリ)でのみ稼働**。サーバーには置いていない
- ローカルでビルド → Git → Vercel にデプロイ

**リポジトリ確認で判明した実態(2026-09-05・github.com/shinmori2020/nordic-works)**
- `scripts/export-wp-data.mjs` で WP REST → JSON + 画像 をビルド前に書き出し、`web/data/` に同梱。`DATA_SOURCE=static` で読む。Vercel は Local に一切アクセスしない(README「落とし穴7」)。**新規サイトはこの仕組みを流用する**
- `DATA_SOURCE=api` に切り替えるだけでWPホスティング移行に対応(二重化設計)
- 公開HTMLは Suspense ストリーミング+ `NEXT_LOCALE` cookie 読み取りにより**動的レンダリング**になっている。README の「静的サイト生成」と食い違う(後付けの next-intl が原因と推定)

**この構成から確定する事実**
- 「ISRかSSGか」の宿題:データ取得は静的(JSON)、レンダリングは cookie により動的。新規サイトは多言語なしなので cookie を読まない設計にすれば静的化できる
- コードに `revalidate` があっても、再生成時に参照先のWP APIがローカルにあり到達できないため機能しない
- Local を閉じている間、WordPress 側は外部からアクセス不可
- **サーバー費用ゼロで運用できている**(新規サイトも同様に追加コストなしで可能)

**説明時の正確な言い方(誤解を招かないため)**
> デモはコスト削減のため WordPress をローカル環境で運用し、静的生成した状態を公開しています。実案件では WordPress をサーバーに設置し、公開ボタンを押すと数分以内に自動反映される構成(ISR / On-Demand Revalidation)にします。

構成の違いを説明できること自体が理解の証明になるため、隠さず伝える。

### 5-3. 「Nordic Works と差分が薄い」への対処

同構成を選んだため差分が課題になる。以下のうち1〜2個を効かせる。

1. **業種を変える(最重要)** — ディレクション / デザイン / 導線 / フォーム項目の判断が丸ごと別物になり、章2・章4の中身が変わる
2. **記録前提で作ること自体** — 初案・却下理由・プロンプト変遷・実測の有無が構造的な差分になる(§1-1)
3. **フォーム完全動作の実装** — 章3に直結。ただし機能を増やすと記録が薄まるため、フォーム周りだけに絞る

### 5-5. 決定:会員機能・DBは記録用サイトに入れない(2026-09-05)

本チャットで「DBを活用して会員機能などのあるもの」という希望が出ていたが、以下で決定。

**決定:会員機能・DBは記録用サイトに入れず、PsychSafe Score 側で扱う。**

- **技術的制約による決定ではない。** Next.js はページ単位でレンダリング方式を混在でき、SSGの静的HTMLからでもブラウザ経由でSupabaseを呼べばログインもDB書き込みも動く。Vercel上ならRoute Handlerも動く。動かないのはWordPressを参照する処理だけ(Local運用に由来)で、Supabase側には及ばない
- 判断したのは「動くか」ではなく「規模を許容するか」
- §5-6「記録用サイトは小さいまま維持する」の**最初の適用場面**。ここで例外を作ると以降の判断が緩む
- 章立ては6章のまま維持。対象読者を「AIで自作して止まった人」に固定する。認証・DBの章を足すと読者が「アプリを作りたい人」に広がり、一貫性が薄まる
- 記録材料(RLS未設定で他人のデータが見える / service_role key の露出)は失われない。PsychSafe は Supabase + RLS が中核なので、そちらの方が自然に深く書ける

### 5-6. 制作欲求の切り分け(前提)

「機能を盛り込んだ見栄えのいいサイトを作りたい」という動機について、**受注のためではなく作ること自体の欲求**であることを本人が明言。以下で整理する。

1. **これは営業施策ではないと明記する。** 制作欲求に基づくものは受注への寄与を成功条件としない。評価軸の異なるものを同じ物差しで測らないための保険
2. **時間の枠を分ける。** 営業・記録用サイトの時間と、制作欲求の時間を別枠にする。枠内なら罪悪感を持つ必要はない
3. **記録用サイトは小さいまま維持する。** 機能を足したくなったら PsychSafe Score 側に足す(ただし§5-1の「判断が発生する最小限」は下回らない)
4. **順番は記録用サイトが先。** 逆にすると楽しい方に時間が吸われて始まらない。意志ではなく順番の問題として処理する

制作欲求で作ったものも、アプリ案件への即答根拠 / 制作会社パートナー営業での評価 / 章6の記録材料として副次的に機能する。

**補足:** 動機が制作欲求であることと、成果物が営業に効くかどうかは独立している。現に、この計画で最も価値が高いと判定した記録材料(§6-3の2層構成の判断理由)は、制作欲求で作った Nordic Works から出てきたもの。**作りたいものを作りながら、判断が発生した瞬間だけ記録する**なら、制作の楽しさを損なわない。

## 6. 機能計画(これまでに出ている材料)

新規サイトの機能は未決定。以下は決定の材料として、これまでに出ている3つの文脈の機能計画を整理したもの。

### 6-1. 実績サイトに必要な機能レベル(基準)

Reactの実績は機能の数より**実務パターンの網羅**が重要、という基準。題材は学習用(TODOアプリ等)ではなく、実在しそうな業種サイトとする。

| 層 | 機能 |
|---|---|
| 最低ライン | コンポーネント設計 / 状態管理 / API連携 / レスポンシブ |
| 実務レベルの証明 | バリデーション付きフォーム / ルーティング / 検索絞り込み / CMS連携 |
| 差別化 | Next.jsのSSG・SSR / TypeScript / パフォーマンス数値 |

**技術選択に関する構造(判断材料):** ヘッドレスWPは指名需要がほぼなく、クライアントは技術名ではなく**症状**(遅い / リニューアル / 更新できない)で発注する。技術構成は「商品」ではなく提案時の解決策・差別化材料として機能する。

### 6-2. Nordic Works の未実装(既存サイト)

**残タスクとして挙がっていたもの**

| 機能 | 対応する層 |
|---|---|
| 記事検索・絞り込み | 実務レベルの証明 |
| フォームの完全動作(Contact / Newsletter の2箇所) | 実務レベルの証明 |
| 「このサイトについて」ページ(構成図・Lighthouseスコア・WP管理画面の更新デモ) | **営業面の施策**。ヘッドレスWPは完成品を見ても普通のサイトと区別がつかないため、「見えない技術を可視化する」ことが目的。本計画(記録を成果物にする)と発想が同じで、既存サイト側の小さな先行実装にあたる |
| ISR / SSG どちらの構成かの把握と説明準備 | 差別化(SSG/SSR) |

### 6-3. SaaSアプリ「PsychSafe Score」(設計済み・着手保留)

Nordic Works の Services 03 に登場する架空サービスを、実際に動くWebアプリとして作る構想。マーケティング層(既存サイト)とプロダクト層(SaaS本体)の2層構成。別リポジトリ・別Vercelプロジェクト(モノレポは不採用)。

**2層構成にした判断理由(記録材料として価値が高い):**
> 1つのサイトに全機能を詰め込むとリアリティが壊れて営業力が落ちる。B2B SaaS という文脈を作ることで、認証・課金・AIがあって当然という状態にし、自然に収める。

これは**AIには出せない判断**である。「認証を実装して」と言えばAIは実装するが、「この題材にその機能を置くと不自然になる」は判断できない。§3-4の「ディレクション:スコープの線引き」に該当する。Nordic Works 制作時に実際に働いた判断であり、**記録が残っていない既存サイトから唯一サルベージできる判断**でもある。

**自己適用:** 新規サイトでも同じ判断が発生する。「記録のために機能を積む」と、まさにこのリアリティ破壊が起きる。**記録が目的だからこそ、題材として不自然な機能は入れない。**

**最小機能セット6つ**
1. 会員登録・ログイン
2. 10問の診断機能
3. ダッシュボード + グラフ + 履歴
4. AIレポート生成
5. Freeプラン制限と Stripe 課金
6. 設定ページ

**構築フェーズ**
フェーズ1(認証 + 診断 + 結果保存)→ 2(ダッシュボード・グラフ)→ 3(AIレポート)→ 4(Stripe課金)→ 5(PDF出力・ダークモード・磨き込み)。各フェーズごとにデプロイして動く状態を保つ。

**スタック**
Next.js (App Router) + TypeScript / Supabase(認証・PostgreSQL・RLS)/ Stripe テストモード / React Hook Form + Zod / Recharts / Vercel AI SDK

**内部構造**
UI層(RSC中心、インタラクティブ部分のみClient Component、shadcn/ui)とサーバー層(データ変更はServer Actions、Stripe WebhookやAIストリーミングはRoute Handlers)に分離。境界は全てZod検証。

**品質基盤**(フェーズ2完了後に後乗せ)
TypeScript strict / Vitest ユニットテスト / Playwright E2E / GitHub Actions CI / Sentry エラー監視

**フェーズ1の着手手順**
1. セットアップ(create-next-app、Supabaseプロジェクト、環境変数。service_role key をクライアント側に出さない)
2. DBスキーマ(profiles / diagnoses の2テーブル、質問はコード内定数。**全テーブルでRLS有効化が最重要**)
3. 認証(**@supabase/ssr を使用**。古い auth-helpers をAIが出してくるため明示指定。middlewareで /dashboard を保護。Googleログインは後回し)
4. 診断機能(10問、React Hook Form + Zod、ステップ形式。**スコア計算とDB保存はServer Action側**)
5. 結果表示ページ → デプロイ

**未決定**
質問10問の内容とスコア算出ロジック / カラム設計とRLSポリシーの具体文 / 画面デザイン・UI設計 / AIレポートのプロンプト設計 / Stripeのプラン設計(価格・制限の具体値)

- 全テーブルでのRLS有効化
- スコア計算をクライアント側に置かない(Server Action側で行う)

### 7-4. 賃貸・売買の両方を扱う理由

「売却・査定」(売買向け)と「オーナー向け」(賃貸向け)の両ページを採用したことで、賃貸仲介+売買仲介+賃貸管理を一社で行う設定になった。

この形は地域密着型の不動産会社では一般的とされる(不動産仲介向けクラウドFacilo・2026年1月)。首都圏では仲介専業もあるが、地方では仲介と管理を兼ねる会社がほとんどという実務者の証言もある(LIFULL HOME'S)。大阪の地域密着会社という設定なら不自然ではない。

収益構造は2種類(仲介=契約時の手数料の単発型 / 管理=毎月の管理料の継続型)。この理解がオーナー向けページの訴求(管理戸数・入居率・空室期間)と、宅建業法表示の「取引態様」の根拠になる。

**AI検索に載せるための実装をすべて行った上で、noindex にする。**

- 実装するもの:構造化データ(Organization / RealEstateListing / FAQ)、明確な会社情報、llms.txt、クロールしやすいHTML構造
- noindex にする理由:架空の不動産会社がAI検索で実在の会社として引用されるリスク。AI検索は要約して提示するため「架空」の表記が落ち得る。実在の人が問い合わせを試みる実害を避ける
- 記録上の価値:「実装は存在するが効果は出ない状態」を意図的に作ることで、実装力と判断力を1箇所で見せられる。載せた場合には取れない記録
- 前提:noindex と AI検索露出は両立しない(AI検索も同じインデックス・クローラーを使い、noindex を尊重する)
- 「自サイトをLLMO実証にする」施策は撤回済み(引き継ぎ総括§4)のため、露出させる方向には戻さない
- 記録ページ(このサイトについて)のみ index にするかは別途判断

### 7-11. 次に決めること

**物件データの設計**(会社設定の直後に着手)。検索に使う項目(タクソノミー)と表示だけの項目(フィールド)の分け方、賃貸と売買の投稿タイプの分け方、架空データの作り方(件数・緯度経度・写真)。

その後、デザイン基準 → 実装。

### 8-1. 3層の役割

### 8-2. 構成に関する判断(記録対象)

- **`config/site.ts` に架空情報を集約**:J-010〜012(架空表記の統一)を「ルール」から「コードの構造」に落とす。18ページに散らばると1箇所だけ実在っぽい番号が残る事故が起きる
- **`rules/static-rendering.md`**:Nordic Works が cookie で動的化した教訓をルール化。前作の失敗を次作のルールに変換した例
- **`web/e2e/` を置く**:Nordic Works は「テストを書かない」と決めた。記録用サイトで先にテストとCIを済ませる(PsychSafe の後乗せ予定を前倒し)
- **`docs/metrics/`**:Lighthouse のレポート本体を残す。数字だけでは自己申告になる
- **入れないもの**:`state/*.json`(記録シートと二重管理・保留)、`api/preview` `api/revalidate`(Local運用では本番で動かない・Nordic Works で証明済み)、`agents/` `workflows/`(規模不相応)
